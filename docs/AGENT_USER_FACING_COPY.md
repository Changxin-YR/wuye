# 面向用户文案规范（去内部术语）

> 适用范围：AI 办事页面（`templates/ai.html`、`static/js/app.js`）、Agent 在对话气泡里
> 直接给出的回答、以及网页端确认卡片上的文字。
>
> **不适用**：发给模型的内部提示（`config/agent_system_prompt.md`）、工具返回给模型的结构化
> 结果（`ok/code/message/terminal`）、审计记录、代码与测试里的风险常量。这些地方必须保留
> 严谨表述，不能为了“说人话”而丢掉授权依据、状态码和审计口径。

## 1. 为什么要有这份规范

用户是物业工作人员和业主，不是系统维护者。他们不需要知道系统内部把操作分成几个风险档、
由哪个服务执行、数据经过哪些处理。他们只关心三件事：

1. 我这件事办成了没有；
2. 系统要我补什么信息、做什么确认；
3. 出了问题我找谁。

因此：**内部术语一律不进入用户可见区域**，需要表达同样的意思时，翻译成用户视角的
“会发生什么”。

## 2. 术语对照表（左=内部，右=用户可见）

| 内部表述 | 用户可见表述 |
| --- | --- |
| Agent / 办事 Agent / 数字代理 | 助手 / 办事助手（“AI 助手”可保留） |
| R0 | 只读查询（不会改动任何数据） |
| R1 | 普通操作 |
| R2 | 重要变更 |
| R3 | 高风险操作 |
| 风险等级：R2 | 重要变更 |
| 风险等级：R3 · 执行策略：人工确认 | 高风险操作 · 需要你确认 |
| execution_mode: AUTO / CONFIRM / READ_ONLY | 系统自动执行 / 需要你确认 / 只读查询 |
| 鉴权、权限校验、DataScope | 权限、能看到哪些数据 |
| 后台业务服务 | 后台（系统） |
| 后端 / 前端 | 后台 / 页面 |
| 落库、持久化 | 保存、记入系统 |
| 回执 / 后台回执 | 处理结果 |
| 待确认卡片 / 操作卡片 | 确认卡片 / 待确认操作 |
| 规划器、Planner、Tool、lookup、execute、propose | （不出现）直接说“正在查询”“已提交” |
| 意图、槽位、候选、消歧 | 不出现；必要时说“请补充能区分的信息” |
| 澄清（动词） | 请补充 / 请说明 |
| 会话标识、token、请求 ID | （不出现） |
| 模型、接口、超时、SSE、API Key | 助手服务、连接；配置类问题提示“请联系管理员” |
| 上下文、脱敏、最小化 | 不出现（安全说明用“发送给助手的信息尽量精简”） |
| ID、version、版本号 | 不出现；用业务名称、工单号、房号、车牌号 |
| 审计 | 操作记录（面向管理员时可保留“审计”） |
| 幂等、去重、重复提交 | “不会重复提交” |
| 确认卡片字段名 `version` / `auth_version` | 记录最新状态 / 账号最新状态 |
| 确认卡片字段名 `id`（记录主键） | 记录编号 |
| 确认卡片字段名 `community_ids` | 涉及小区（值写“共 N 个”，不列数据库编号） |
| 确认卡片字段名 `remark` / `content` | 处理说明 / 详细内容 |
| 住户/维修人员/业主等字段名带 `_id` 后缀 | 去后缀：住户账号、维修人员、业主、房屋 |
| Agent 授权过期、角色变化等助手报错 | 这次办理的授权已过期，请重新发起 / 你的岗位或负责范围变了，请重新发起一次办理 |

## 3. 写作规则

1. **先说结果，再说下一步。** “已提交报修，工单号 A1024” 优于 “提交动作已执行成功”。
2. **说明会发生什么，而不是它叫什么。** 用“确认后才会真正删除”代替“R3 人工确认”。
3. **不承诺没发生的事。** 只有系统真正写入成功才可以说“已办成/已保存”；只是准备好了，
   要说“已准备好，等你确认”。
4. **不让用户提供系统已知的信息。** 不要索要内部编号、版本号；能查的自己查。
5. **错误文案给出路。** 权限不足 → 说明换个有权限的账号或联系管理员；找不到 → 说明
   核对哪里；连接失败 → 说明可稍后重试，并指出哪条业务链路不受影响。
6. **专有名词只在配置/管理场景出现。** 连接检测、模型名、API 地址这类信息只在管理员
   可见的诊断按钮后面出现，普通对话里不出现。
7. **同一件事只描述一次。** 卡片标题已经写了“高风险操作”，下面不再重复“风险等级：R3”。

## 4. 落地位置

- `templates/ai.html`：页面标题、状态行、说明段、按钮、空态提示、页脚说明。
- `static/js/app.js`：气泡内的状态前缀、确认卡片标题与说明、按钮、错误提示。
- `app.py`：**仅** planner 兜底回答（`CLARIFY/DISAMBIGUATE/DENY` 三句）；流式错误文案
  需与流式过滤的负责人协调后再改。
- `agent_planner_core.py` / `agent_planner.py`：planner 的澄清问句由
  `agent_planner.py::_clarification_text` 统一生成，`agent_planner_core.py` 只产出
  `missing_fields`（内部槽位名，不出现在页面上）。改问句只改 `_clarification_text`，
  槽位名保持原样，否则会破坏 planner 与 `app.py` 的对应关系。
- `agent_tools.py::describe`：确认卡片的字段名（`changes[].label`）由
  `agent_card_label()` / `agent_card_labels()` 生成，来源顺序是
  `AGENT_CARD_LABELS` → `agent_tools.LABELS` → `management_ui.LABELS` → 兜底“本次改动”。
  内部参数名（`version`、`community_ids`…）绝不会原样出现在卡片上；`community_ids`
  这类编号清单只显示“共 N 个”。这里只改展示文案，不动参数名与权限判断。
- 回归用例：`tests/test_ai_chat_precise_clarification.py` 断言的是“文案具体、且不泄漏
  Policy/DataScope 等内部策略”。改文案时同步更新断言字符串，**不得**放宽为“不检查”。
- `tests/test_ai_page_plain_language.py`：页面级回归，渲染 `templates/ai.html` 后扫描
  可见文本，出现内部术语即失败（此文件为文案专用，改动文案时改它，不要改别人的用例）。
- `tests/test_agent_action_card_copy.py`：确认卡片回归，覆盖 `describe()` 的字段名翻译
  与真实 `propose()` 落库后 `/ai/actions` 返回的卡片文案。
- `artifacts/copy-verify/dom-harness.js`：用 DOM 桩跑真实 `static/js/app.js`，检查卡片
  渲染出来的每一行（含字段名）是否含内部术语。

## 5. 已完成

`app.py` 里原本两处带内部术语的用户可见文案已经改完（与 `app.py` 改动者确认后落地）：

| 位置 | 原句 | 现句 |
| --- | --- | --- |
| planner 兜底 `CLARIFY` | 请补充必要的业务信息后再操作。 | 还需要补充一些信息才能继续办理。 |
| planner 兜底 `DISAMBIGUATE` | 找到多个匹配对象，请提供更多信息以确认。 | 符合条件的有好几条，请再补充一点信息，确认是哪一条。 |
| planner 兜底 `DENY` | 该请求不在当前登录身份允许的范围内。 | 当前账号没有这项权限。可以换一个有权限的账号办理，或联系物业管理员。 |
| 高风险操作重新验密码（401） | R3 操作需要重新验证当前密码 | 这一步需要重新输入你的登录密码确认身份 |
| 模型没返回有效文本 | 百炼未返回有效文本 | 智能助手没有返回有效回答，请重试 |
| 回答期间数据变化 | 业务数据在回答期间发生变化，请重新提问以获取当前信息 | 你说的事情刚刚有了新变化，请重新说一遍，我按最新情况处理 |

`tests/test_ai_chat_precise_clarification.py` 的 DENY 断言已同步更新（断言意图不变：
文案对用户可读、且不泄漏 Policy/DataScope）。
